Aim and Objectives

Experiment 03: Cryptography and System Security (CSS) Lab

Aim

To study, simulate, and analyze the operational impact of Denial of Service (DoS) and Distributed Denial of Service (DDoS) attacks against a centralized server, and to evaluate the efficacy and inherent architectural limitations of per-source rate limiting defenses.

Key Focus: Compare how single-source flooding behaves differently from multi-source distributed botnet flooding when filtered through edge rate limiters.

Objectives

  • Understand the fundamental distinction between single-source DoS and multi-source botnet DDoS attacks.
  • Analyze server queue saturation and request drop rates when offered aggregate traffic exceeds server processing capacity.
  • Simulate per-source rate limiting (filtering requests on an upstream firewall / proxy) and observe why individual rate limits neutralize high-volume DoS but fail against distributed low-rate DDoS botnets.
  • Record comparative quantitative observations across Baseline, Unmitigated DDoS, and Protected phases.
  • Identify enterprise defenses (Anycast CDN, scrubbing centers, Web Application Firewalls) necessary to mitigate real-world DDoS attacks.

Theory: DoS vs DDoS & Protection Mechanisms

Foundations of Availability in the CIA Triad

1. Server Capacity and the Availability Triad

Every physical or virtual server has finite finite compute resources: maximum network socket allocations, CPU cycles, RAM buffers, and application worker threads. This maximum sustainable processing rate is defined as Server Capacity (measured in requests/second). When incoming traffic arrival rates exceed server capacity, requests accumulate in connection queues until buffers overflow, causing the server to drop incoming connections and deny service to legitimate users.

2. Single-Source DoS vs Multi-Source DDoS

In a Denial of Service (DoS) attack, a single attacker machine floods the server with an extraordinarily high request rate (e.g., 120 req/s from one IP). Because this single IP transmits orders of magnitude above normal client activity, it is readily detectable by threshold inspection.

In a Distributed Denial of Service (DDoS) attack, the adversary harnesses a Botnet—thousands of compromised endpoints (PCs, IoT devices, cloud servers) coordinated through Command and Control (C2) channels. Each individual bot transmits at a deceptively modest rate (e.g., 5 to 10 req/s), indistinguishable from authentic human behavior. However, the aggregate sum across all bots overwhelms server capacity.

3. Volumetric vs Application-Layer Floods

Volumetric Floods (Layer 3/4): Aim to saturate the network pipe via UDP floods, ICMP storms, or DNS amplification.

Application-Layer Floods (Layer 7): Target web application endpoints (HTTP GET/POST) by making computationally expensive database queries or file downloads, exhausting server thread pools with comparatively lower bandwidth.

4. Per-Source Rate Limiting & Why It Fails Against DDoS

Per-source rate limiting caps incoming requests allowed from any single client IP address within a time window (e.g., max 10 req/s per IP).

  • Against DoS: Extremely effective. The single source sending 120 req/s is restricted to 10 req/s. 110 req/s are blocked, protecting the server.
  • Against DDoS: Ineffective. If 200 bots each send 5 req/s, every bot stays strictly below the 10 req/s threshold. Zero bot requests are blocked, and all 1,000 req/s hit the server.

5. Real-World Defenses

Industry production architectures defend against DDoS using multi-layered edge technologies:

  • Anycast Content Delivery Networks (CDNs): Disperse regional volumetric floods across globally distributed edge Points of Presence (PoPs).
  • DDoS Scrubbing Centers: Specialized cloud inspection facilities that separate malicious packet floods using deep packet inspection (BGP diversion).
  • Web Application Firewalls (WAF) & Behavioral Analysis: Enforce CAPTCHAs, cryptographic browser proof-of-work challenges, and TLS fingerprinting.
  • Host Firewalls (Conceptual): Linux packet filtering systems (such as iptables / nftables with connection tracking modules) can enforce rate thresholds at the kernel boundary before packets hit application processes.
Limitations of This Educational Model:
This virtual lab uses a pure numerical aggregate request model (req/s). It assumes attack sources are discrete and identifiable. It does not model TCP handshakes, SYN queues, socket exhaustion, latency distributions, or spoofed IP headers. In real networks, simple rate limiting cannot stop true DDoS.

Procedure: DDoS & Protection Experiment

Step-by-step workflow for running simulations and recording observations

  1. Navigate to Interactive Simulation: Open Section 4 ("Interactive: DDoS Simulation") from the toolbar or the right-side resource panel.
  2. Phase 1 - Run Baseline Normal Traffic Preset: Click the Normal (20 / 0 / 100) preset button. Verify:
    • Legitimate traffic = 20 req/s
    • Server capacity = 100 req/s
    • Attack traffic = 0 req/s
    Click Run Simulation.
    Expected observation: Status is Normal, 0 dropped requests, server utilization ~20%, CPU usage low, service state Responsive. Auto-recorded to Observation Table row 1.
  3. Phase 2 - Run DoS Single-Source Flood Preset: Click the DoS (20 + 1x120 / 100) preset. 1 attacker source emits 120 req/s. Click Run Simulation without protection.
    Expected observation: Server is Overloaded, 40 requests dropped per second, legitimate traffic suffers severe drop rate.
  4. Phase 3 - Run Unmitigated DDoS Attack Preset: Click the DDoS (20 + 5x40 / 100) preset. 5 distributed attack nodes emit 40 req/s each (total attack 200 req/s). Keep protection turned OFF. Click Run Simulation.
    Expected observation: Offered traffic is 220 req/s against 100 capacity. Status is Overloaded, 120 req/s dropped, CPU near 99%, service state Unresponsive. Auto-recorded to Observation Table row 2.
  5. Phase 4 - Test DDoS with Per-Source Rate Limiting: Click the DDoS + Protection preset (20 legit, 5x40 attack, limit 10/source). Click Run Simulation.
    Expected observation: Rate limiter blocks 150 req/s (each bot capped from 40 to 10). Arriving traffic is 70 req/s, accepted is 70 req/s, 0 dropped. Status recovers to Normal. Auto-recorded to Observation Table row 3.
  6. Phase 5 - Stress Test Distributed Bot Scaling: Manually increase attacker count to 50 sources, keeping the 10 req/s limit. Click Run Simulation.
    Expected observation: Even with 10 req/s per source, 50 bots yield 500 req/s allowed. The server enters Overloaded status with 420 dropped req/s, proving that simple per-source rate limiting collapses under true distributed scale.
  7. Review & Verify Observations: Open Section 5 ("Observation Table") to review the auto-populated 3-phase comparative data matrix.
